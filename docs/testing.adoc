This page describes what the test suites verify and where their boundaries are. For application code, start with the practical guide rather than the test fixtures.

== Run Tests

[source,shell]
----
mvn test
mvn verify
----

Tests use mocks, loopback services, and isolated child JVMs instead of requiring live Kafka, Redis, or Elasticsearch servers. Cluster tests require local port binding and permission to launch child JVMs. HTTP/3 additionally needs a compatible native QUIC runtime. See link:development.adoc[development] for the build toolchain and workflow checks.

== Clustered FlowId Coverage

`ClusteredFlowIdTransportTest` starts three Vert.x nodes in a private Hazelcast cluster, using loopback TCP and ephemeral ports with multicast and automatic discovery disabled.
Consumers exist only on the receiving node, so requests and replies cross the clustered EventBus network transport.
The 55 cases cover every sender/receiver codec pair, unchanged and replaced remote values, failure replies, overlapping flows, messages without metadata, and generated ServiceProxy calls across three deployed verticles.
All three profiles round-trip a 64 KiB UTF-8 JSON payload over TCP. Codec tests also reject payloads one byte over the limit and gzip streams with truncated or damaged trailers.
They also cover removal, stale-header suppression, explicit re-addition, and removal while a network reply is pending.
Removal markers are checked across three nodes and on return to both empty callers and callers with existing values.
They assert distinct remote instances with matching values and preservation of the caller's original instance.
All nodes in this class run in one test JVM; separate-process coverage is provided below. Neither suite covers TLS, node loss, or network partitions.
Run this coverage with `mvn -Dtest=ClusteredFlowIdTransportTest test`; it is also included in the standard test suite and closes its nodes after execution.

The ServiceProxy scenarios run on event-loop and worker verticles, with legacy, JSON, and gzip writers on A, B, and C respectively:

[source,text]
----
A adds flow-A -> B receives flow-A, replaces with flow-B -> C receives flow-B, replaces or removes it
A retains flow-A <- B retains flow-B <- C replies or fails
----

The tests assert values and local object identity at every stage, without manual context wrappers inside the verticles.
The test-only service interface is processed during test compilation; generated proxy and handler sources under `src/test/generated` are excluded from version control.

`ForkedClusterFlowIdTransportTest` deploys the same generated ServiceProxy contract across three JVMs: A runs in the test process, B is an event-loop verticle in a JSON-writing child JVM, and C is a worker verticle in a gzip-writing child JVM. A writes legacy values.
Its six scenarios cover unchanged values, replacement, removal, forwarding an existing removal, explicit re-addition, and failure replies.
Three additional repeated cases each launch a batch of 12 concurrent calls mixing all six scenarios. A test-only barrier confirms all 12 requests overlap on both remote nodes before allowing replies, with bounded waits through per-request timers rather than blocking the event loop or worker.
Six further cases deploy callers on event-loop, worker, and virtual-thread verticles. Each caller replaces or removes its FlowId while a ServiceProxy call is pending; concurrent remote replacements, removals, and failure replies preserve that newer local state, including its object identity or removal marker after a subsequent timer. The remote reports still contain the original request's serialized FlowId rather than the caller's later mutation.
Unique request tokens and timestamps detect cross-request leakage, and each node verifies local object identity after its timer and downstream return, including failure paths.
The tests verify distinct process IDs, incoming request and reply headers, timestamps, and preservation of local instances on return, including a subsequent timer callback.
Each child has independent provider discovery and JVM codec configuration; there is no shared Java heap between nodes.
The fixture uses a private loopback Hazelcast cluster with ephemeral ports and bounded readiness waits. It closes child stdin for graceful shutdown, checks normal exit, and forcibly terminates any child that exceeds its shutdown timeout.
Run just this coverage with `mvn -Dtest=ForkedClusterFlowIdTransportTest test`; it also runs in the standard test suite and requires permission to launch Java child processes and bind loopback ports.

== Collection Transport Coverage

`ContextCollectionsIntegrationTest` registers external map/set/list codecs and factories in isolated child JVMs. Its core-only runtime exercises EventBus and direct carrier operations without optional clients or JUnit. A separate runtime includes WebClient but excludes Kafka and JUnit, exercising all three collection types over HTTP/1.1, HTTP/2 upgrade and prior knowledge with both Vert.x implementations, and direct HTTP/3 over QUIC. Request and response versions are asserted, so protocol fallback cannot satisfy the tests. HTTP/3 uses a temporary certificate explicitly trusted by the client with hostname verification enabled; it requires the same platform-native QUIC runtime as the generic HTTP/3 tests.

HTTP cases run on event-loop, worker, and virtual-thread callers with each FlowId writer profile. A handshake delays the server response until the caller has changed its own collections, proving that the wire request remains the send-time snapshot while return import applies the codecs' whole-item replacement policy.

[cols="1,2",options="header"]
|===
|Sent collection state |Server behavior and caller result
|Values |Server changes map entries, set membership, and list positions/duplicates. Returned snapshots replace the caller's in-flight changes; older captured snapshots remain unchanged.
|Present empty |Server receives typed empty values, then removes the whole items. Returned removal markers replace the caller's newer populated collections.
|Explicit removal |Server imports and verifies the marker state without factory revival, then explicitly replaces it. Returned values replace the caller's independently reintroduced snapshots.
|Absent |Server receives no collection item or removal marker. Explicit server replacements return normally; neither missing headers nor import invokes initialization factories.
|===

The server also replaces its FlowId before replying. The caller retains its existing FlowId instance, including an in-flight local replacement or removal marker, independently of collection return policies. Request/response and timer callbacks retain their original contexts and current item references. Private storage is neither exported nor leaked between sequential requests on the shared client, and ordinary payloads/application headers remain unchanged. Responses carrying metadata retain `Cache-Control: no-store`.

A Kafka-only child excludes WebClient and JUnit and uses the Vert.x producer with Kafka's native `MockProducer`. For each caller threading model and FlowId writer profile, it sends values, present-empty collections, explicit removal markers, and absent metadata through two scoped consumer handlers. The producer changes its collections immediately after sending; the first consumer still receives the send-time snapshot. That consumer either edits/replaces all three collections or removes them, then forwards another record. The second consumer verifies decoded values, list order/duplicates, or removal markers before making its own local changes. Nested dispatch restores the first consumer's context and stored references; asynchronous completion and timers preserve the producer's newer snapshots and original FlowId. Private storage stays local, and imports do not invoke initialization factories. These are one-way deliveries: acknowledgments never import consumer changes back into the producer.

Kafka records are transferred from mock-producer history into native consumer records with copied header bytes. No broker, polling loop, partition assignment, or broker-side delivery guarantee is exercised. Run the local collection runtimes with `mvn -Dtest=ContextCollectionsIntegrationTest test`; no external services are required.

`ForkedClusterCollectionsTransportTest` uses three JVMs in a private loopback Hazelcast cluster: caller A, worker B, and worker C. The caller explicitly installs the external collection codecs, while both children discover them through SPI; FlowId writers use legacy, JSON, and gzip respectively. Direct request/reply cases use A/B. All three caller threading models send values, typed empty collections, removal markers, and absent metadata to B. Replies either replace all three collections (including edited entries, membership, and list order/duplicates) or remove them. The caller changes its collections and replaces/removes its FlowId after sending: returned collections follow their whole-item replacement policy, while the newer caller FlowId or removal marker survives. Tests verify process IDs, timer/context identity, unchanged older caller snapshots, private-storage isolation between sequential requests, and no factory calls on remote import.

Overlapping clustered cases run two eight-request batches per caller threading model. Each batch mixes all four incoming states with returned replacement/removal, using a distinct token for every request. The remote worker waits until all eight requests arrive before any reply can complete; every response must report eight peers. Each request retains its own timer context, incoming snapshots/removal state, FlowId, and private item while waiting. Caller assertions verify returned data against its own token, current FlowId/removal, unchanged older snapshots, and private storage. Successful caller deployments are undeployed after the joined batch, and the child checks that no batch state remains at shutdown.

The same remote worker also registers the generated `ClusterFlowService` through `ServiceBinder`. Collection-specific ServiceProxy cases use `ServiceProxyBuilder` and the generated client/handler over the network, not a hand-written proxy double. They repeat all 24 state/model/replacement-or-removal cases and six coordinated eight-call batches. Both entry points share the remote scenario implementation and the caller's context, snapshot, FlowId, and timer assertions; the direct EventBus path additionally inspects reply headers for private metadata. ServiceProxy results are JSON reports encoded as strings, keeping collection metadata outside the application payload.

Service failure cases repeat the 24-case matrix after the remote worker changes its collections and FlowId, then returns a controlled `ServiceException`. The caller verifies the actual failed future, recipient-failure type, error code, report token, and callback context before inspecting metadata. Returned collection replacements/removals still replace pending caller snapshots, independently of its newer FlowId value/removal and private storage. Six further sixteen-call batches mix successful and failed service calls, with both collection outcomes for every incoming state. Every call waits for all sixteen peers, and failure callbacks, normalized test-report continuations, and timers retain the proper caller context. Expected errors are decoded into reports only by the test harness; the generated service's future remains failed. Child batch cleanup includes failed calls.

Twenty-four additional A/B cases hold a remote service reply until the caller observes native `TIMEOUT`. A test-only control endpoint confirms remote arrival, releases the held context after expiration, and reports actual map/set/list and FlowId headers captured at late outbound dispatch. Control replies explicitly carry no managed metadata, so coordinating the test cannot replace caller snapshots. The late reply contains either edited collection replacements or whole-item removals, plus a remote FlowId replacement; the expired caller retains its current collection references, FlowId value/removal, and private item. A subsequent generated service call inspects the caller's current values, emptiness, removals, or absence in B before replying normally. Timers retain the resulting caller references, and child shutdown checks that held replies and captured headers were consumed. These cases cover all three caller threading models, but do not claim overlapping timeouts, late service errors, or broker/network-failure recovery.

Forty-eight A -> B -> C ServiceProxy cases exercise forwarding and return through all three JVMs, across incoming states, caller threading models, final replacement/removal, and success/failure. B replaces values, removes a present value, explicitly reintroduces a removed item, or creates a previously absent item according to the scenario; it also forwards typed empty values and existing removal markers. C validates the actual forwarded state, changes its collections and FlowId, and replies normally or with the controlled service error. Returned collections replace B's sent snapshots and then A's pending snapshots, while B retains its own newer FlowId and A retains its current value/removal. Private items never cross either hop, and both child process IDs and timers are verified. Service errors retain their code through both generated proxy boundaries.

The clustered fixture uses bounded readiness/shutdown waits, ephemeral ports, and forced child cleanup on timeout, including partial startup failures. Run it with `mvn -Dtest=ForkedClusterCollectionsTransportTest test`; child JVMs and loopback port binding must be permitted. Cluster TLS, node loss, partitions, and concurrent multi-hop failure recovery are separate integration concerns, not claims of this fixture.

`ServiceProxyCollectionsTimeoutTest` separately installs the external collection codecs for local generated-ServiceProxy tests, without changing global SPI registration. Twelve no-handler cases preserve values, typed empty collections, removals, and absent metadata on all three caller threading models. Twenty-four timeout cases hold the server promise until the caller observes native `TIMEOUT`, then release either replacement values or removal markers. An outbound interceptor inspects the actual late map/set/list and FlowId headers, proving that the server exported metadata even though the expired call cannot import it. Caller snapshot references, current FlowId value/removal, and private storage survive timeout and late dispatch. The next service call verifies the caller's current collection contents/removal/absence rather than the late server state; its ordinary reply may decode fresh collection wrappers under their replacement policy, and timers retain those returned references. These are local EventBus timeout/late-reply checks, not additional clustered timeout coverage. Run them with `mvn -Dtest=ServiceProxyCollectionsTimeoutTest test`.

`CollectionCodecTransportTest` adds twelve Unicode/empty/removal round trips through the HTTP and Kafka carriers and 152 rejection/recovery cases through the HTTP carrier and transport engine. The external example codecs reject unsupported versions, malformed JSON, wrong container shapes, non-string/null elements, duplicate metadata headers, and duplicate set elements (list duplicates remain valid). Rejection preserves the exact prior value, empty wrapper, removal marker, or absence, continues healthy FlowId import, and permits the next valid collection import. Error diagnostics omit private text and cause chains even when the context error observer throws. These are codec/carrier boundary tests, not malformed-payload injection into every network protocol.

|===
|Boundary |Deterministic coverage
|Typed storage |Immutable map/set/list snapshots, declaration checks, atomic operations, concurrent writers, lifecycle and factories.
|Runtime discovery |Core-only, HTTP-only, and Kafka-only forked applications; external codecs/factories and all FlowId profiles.
|HTTP |Six wire modes across HTTP/1.1, HTTP/2, and HTTP/3; all caller models and collection states, in-flight edits and return policies.
|Kafka |Mock producer to two scoped consumers; copied header bytes, edits/removals forwarded without acknowledgment back-propagation.

Live Kafka brokers, real Redis/Elasticsearch deployments, node/network failures, and every optional client feature are outside this bounded collection test pass. The separate client-compatibility tests below retain their own success/failure and instance-continuity coverage.

== Client Context Compatibility

The compatibility tests check that a stored `ContextChainDataItem` remains the exact same Java object in the calling context and its asynchronous continuations.
They cover success, failure, fallback, timeout, and overlapping calls where applicable, using transport doubles and loopback servers without external services.

Deployment checks cover event-loop, worker, and virtual-thread models for storage/EventBus call-and-return, HTTP request isolation, Kafka record-handler exception/context restoration, and timers. Timer deployment tests include one-shot callbacks, timer futures, cancellation, and bound periodic callbacks. Virtual-thread checks assert both the context threading model and `Thread.isVirtual()` rather than relying only on deployment success. Clustered ServiceProxy and the other client scenarios retain their separately documented coverage; virtual-thread coverage is not claimed for every client operation.

Local generated-ServiceProxy tests cover native `NO_HANDLERS` and `TIMEOUT` failures on all three threading models with caller values, removal markers, and empty storage. Replies deliberately completed after timeout still export their metadata, but cannot import it into the expired caller. Subsequent calls start with the caller's unchanged state rather than the late reply's value or removal; failure and timer callbacks retain the original caller context.

Imperative virtual-thread tests also exercise `Future.await(...)` and `future.await()` for EventBus request/reply, WebClient, bound foreign results, and timers, including failures and cancellation. They verify context and stored-instance retention after resumption, plus value/removal policy and response-header import when HTTP body decoding fails. Foreign results start incomplete and are completed by a task queued behind the awaiting task. Use these imperative await patterns in virtual-thread verticles, not to block event-loop or worker handlers; awaiting a result does not make unrelated foreign callbacks context-aware.

[cols="1,2",options="header"]
|===
|Client or extension |Tested behavior
|Vert.x ServiceProxy 5.2.3 |Native no-handler and timeout failures preserve caller state; late replies do not update an expired caller or leak into subsequent calls. Clustered request/reply coverage is described above.
|Vert.x Kafka producer 5.2.3 |Send success, submission and acknowledgment failures, and overlapping acknowledgments preserve the caller's instance.
|Vert.x Kafka consumer 5.2.3 |Shared-consumer assignment and polling need `ContextPropagation.bind` to resume on the caller's context, on success and failure.
|Vert.x Redis client 5.2.3 |Success, Redis errors, disconnects, and overlapping pooled calls preserve the caller's instance.
|Vert.x WebClient 5.2.3 |HTTP responses, disconnects, and overlapping requests preserve the caller's instance.
|Vert.x CircuitBreaker 5.2.3 |Operation completion, failure recovery, fallback, timeout, and context updates returned to the caller preserve object identity.
|Vert.x timers 5.2.3 |One-shot callbacks and timer futures preserve object identity on completion and cancellation. Periodic ticks use fresh contexts and need `ContextPropagation.bindHandler`; adapted ticks and isolated flows retain the caller's instance.
|Elasticsearch Java async client 8.15.3 |A controlled transport completes on a foreign thread; `ContextPropagation.bind` preserves the caller's instance on success and failure.
|===

Bind results before attaching application continuations, from within the originating Vert.x context:

[source,java]
----
ContextPropagation.bind(elasticsearch.ping())
    .onSuccess(response -> use(FlowIdContext.get()));

ContextPropagation.bind(sharedKafkaConsumer.poll(Duration.ofMillis(100)))
    .onSuccess(records -> use(FlowIdContext.get()));

vertx.setPeriodic(1000, ContextPropagation.bindHandler(timerId ->
    use(FlowIdContext.get())));
----

The adapter rebinds the result to the calling context; it does not make raw client threads context-aware or attach metadata to protocol messages.
Object identity is a same-JVM guarantee. Transport across process boundaries requires serialization and creates a new instance on the receiving side.
These tests validate client integration at the mocked or loopback boundary, not compatibility with deployed Kafka, Redis, or Elasticsearch servers.


== HTTP Adapter Coverage

Session tests cover HTTP/1.1 and both clear-text HTTP/2 implementations, allowed and denied origins, values, removals, and empty storage. They verify that stale managed session defaults are stripped, application headers and cookies survive, and return metadata follows the same inbound policy as ordinary requests.

Session redirect tests also verify sanitization on each hop, including denied final destinations. Redirect cookies retain native session behavior, while malformed metadata on followed responses is ignored and only the final response can update caller storage.

Loopback tests cover HTTP/1.1 forward proxies and HTTPS through HTTP CONNECT with explicitly trusted temporary certificates and hostname verification enabled. They verify client-default, per-request, and cleared-default proxy settings, FlowId values/removals/empty storage, stale-header stripping, ignored return metadata, payloads, and timer context. CONNECT headers carry no managed metadata. SOCKS, TLS connections to the proxy itself, and HTTP/2-over-proxy behavior remain outside this coverage.

IPv6 loopback tests cover literal `http://[::1]:port` origins, native and explicit matching bracketed Host values, response import, and timer context over HTTP/1.1 and both clear-text HTTP/2 implementations. A conflicting IPv6 Host on HTTP/1.1 still delivers the payload without metadata. In the HTTP/2 tests, Vert.x rejects the conflicting Host/authority pair before the server handler runs with a protocol-error stream reset; an uninstrumented client behaves identically. The adapter preserves that native failure and caller storage, and a subsequent valid request propagates normally. These checks require IPv6 loopback support in the test environment.

Idle-timeout tests verify both sides of that header boundary on event-loop, worker, and virtual-thread callers, with existing values, removal markers, and empty storage. They retain the native timeout failure and caller context; metadata imported before a body timeout remains available in the failure callback and subsequent timers.

Streaming response tests exercise `BodyCodec.pipe` with a synchronous, always-writable sink on all three deployed threading models, over HTTP/1.1 and both clear-text HTTP/2 implementations. They verify header import before the first write and allow the sink to replace or remove its FlowId during consumption; later writes, sink completion, response callbacks, and timers retain that changed state. A first-chunk barrier verifies that the server's storage remains independent after the client mutation.

Both sink-ownership modes are tested: the default codec ends the sink, while `BodyCodec.pipe(sink, false)` leaves it open for application use. After the response completes, caller-owned sinks accept another write and an explicit application end with the same caller context and changed FlowId state.

Controlled asynchronous sinks additionally exercise one native pause/drain cycle, deferred write/end completion, and write/end failures on the same protocol/model matrix. FlowId changes made while paused survive resumption and failure, native sink failures reach the caller unchanged, and server storage stays independent. These sinks complete on the caller context; arbitrary foreign-thread sinks remain outside this coverage.

Caller-owned asynchronous sinks also retain their lifecycle on failure: a failed write still fails the HTTP operation without ending the sink. Explicit application cleanup can subsequently succeed or fail on the same context; an application-owned end failure does not retroactively change a completed HTTP result or its latest FlowId state.

In-flight cancellation tests capture the native `HttpClientRequest` and call `cancel()` either before response headers or after the first streamed write, after both requests have reached the server. Phase counters distinguish these boundaries: before headers there is no response import, body write, or sink completion. Both modes verify peer-observed cancellation, preservation of the caller's latest FlowId value or removal, unchanged native failure delivery, and isolation of another active request on the shared client. HTTP/2 requests share one connection; HTTP/1.1 controls use separate connections because cancellation closes the connection. These checks cover all three deployed threading models and both clear-text HTTP/2 implementations, not cancellation before a connection is acquired.

Ingress-isolation tests start servers from root and duplicated contexts on event-loop, worker, and virtual-thread verticles. They verify that startup storage and earlier server-side request mutations do not leak into later independent requests, including values, removal markers, and empty storage over one reused HTTP/1.1 connection with sequential or pipelined sends. Body and timer callbacks retain the native per-request context, and request mutations leave server startup storage unchanged.

Response-commit tests verify that oversized server metadata and even a throwing error observer leave HTTP payload delivery intact. Stale managed response headers are stripped, server storage is unchanged, and caller values, removals, or empty storage survive. A subsequent valid response can propagate normally, retaining the usual inbound policy and timer context across all three caller threading models.

Application handler failures are not metadata failures. Wrapped and unwrapped HTTP handler tests deliver the original runtime exception or assertion error to the native Vert.x error observer on the same isolated request context. In these tests the application observer replaces/removes its FlowId and explicitly sends a 503 response; the adapter exports that final state without changing the caller's stored instance, later timers, or the next request's isolated storage. Error-response generation remains application-owned, not automatic adapter recovery.

Client application-interceptor tests compare instrumented and native clients across prepare, send, receive-header, and response-dispatch runtime failures. The original exception fails the request future on the caller context without being reported as a metadata error. Failures before response headers import nothing; later failures retain already-imported metadata through timers and export it on a subsequent request. The same shared client remains usable. These interceptors do not modify headers or routing.

TLS tests cover HTTP/1.1 and HTTP/2 with ALPN, using a temporary certificate trusted explicitly by the client with hostname verification enabled. They also verify that mismatched HTTP/HTTPS origin schemes deny metadata propagation without stopping payload delivery, and that untrusted certificates fail the request without changing caller storage. Tests generate their certificate using the running JDK's `keytool`; no private keys are checked in. Separate loopback tests cover explicit TCP socket routing, Host-header overrides, and the proxy cases described above; custom address resolvers and caching-client integrations remain outside these checks.

HTTP/3 loopback tests force HTTP/3 on both peers and assert the actual request and response versions, so TCP fallback cannot mask failures. Three overlapping callers exercise FlowId values, removals, and empty storage, reversed replies, request isolation, exact local instance retention, return-import policy, denied origins, and server/client timers across event-loop, worker, and virtual-thread callers. Certificates are explicitly trusted with hostname verification enabled. Native test artifacts cover macOS/Linux x86-64 and ARM64 plus Windows x86-64; actual execution still depends on the host runtime. Initial HTTP/3 coverage targets direct internal calls, not proxies, Alt-Svc upgrades, connection migration, or fallback behavior.

HTTP/3 failure tests also inject malformed envelopes, oversized values, and duplicate headers on requests and responses. Rejected metadata leaves payload delivery intact even when the metadata error observer throws; diagnostics retain no payload or cause chain. Existing caller values/removals skip response decoding under the usual inbound policy, while empty storage reports the rejected metadata. A subsequent valid exchange on the same client succeeds, with request isolation and caller state retained through body callbacks and timers across all three threading models.

== Kafka Adapter Coverage

Reentrant handler tests use controlled records on all three threading models: an inner invocation restores the outer scope on success, runtime failure, or assertion, without changing the parent flow. They verify isolated private storage, native copying of unrelated locals, unchanged failure identity, record timers after both scopes unwind, and a fresh subsequent record without metadata. Denied outer or inner topics still deliver the payload with empty library storage, ignoring their malformed metadata without reporting a metadata failure; denied inner topics also ignore removal markers. All four outer/inner topic-policy combinations are tested: denial does not suppress a later allowed invocation's fresh import, and unrelated locals retain their native copying semantics. These checks do not add automatic awaiting or ordering of asynchronous record processing.

Invalid application records are not optional metadata failures: synchronous record validation or header-accessor exceptions fail the sender's returned future. Tests compare native validation behavior and preserve accessor-failure identity, input headers/buffers, caller values/removals/empty storage, and subsequent timer context across all three deployed threading models. No record reaches the mock producer on these failures, and a later valid send through the same sender succeeds.

Native-consumer overlap tests deliver three records from one controlled poll, including a metadata-free record, before completing any application work. Results bound with `ContextPropagation.bind` complete on ordinary Java threads in reverse record order, with success and failure cases across event-loop, worker, and virtual-thread deployments. Each continuation and subsequent timer retains its record's exact replacement instance or removal marker; failures retain their identity and consumer-parent storage stays unchanged. The adapter itself does not await these results or serialize record processing.

These overlapping records also forward through a shared sender after asynchronous processing. Downstream handlers import the current replacement or removal only when export is allowed; denied topics still carry the payload and application headers without managed metadata. Forwarding leaves the input record's headers unchanged, acknowledgments retain the forwarding scope, and downstream storage changes do not flow back into that scope or consumer-parent storage.

Mixed-transport tests exercise loopback HTTP/1.1 and direct TLS HTTP/3 -> mocked Kafka -> local EventBus with replacements and removals at every stage. HTTP/3 cases explicitly configure and verify that protocol on both peers, using trusted temporary certificates with hostname verification enabled. They verify caller values, caller removal markers, empty callers, timer callbacks, and isolation of private storage. The HTTP response contains the HTTP producer's current state, not changes made by the Kafka consumer. Tests explicitly coordinate consumer completion; this does not turn Kafka acknowledgments into RPC replies. EventBus replies still apply the normal FlowId inbound preservation policy.

The reverse Kafka -> HTTP direction uses a native Vert.x consumer wrapping `MockConsumer` and a shared WebClient session over loopback HTTP/1.1. Two records overlap before either HTTP server response is released, starting with a wire value and missing metadata respectively. Across all three deployed threading models, each consumer asynchronously replaces or removes its FlowId before sending; allowed origins receive that state and denied origins receive no managed metadata. HTTP server replacements/removals cannot overwrite the consumer's current state, response and timer callbacks retain its scope, and private storage stays local to each record without changing consumer-parent storage.

== Runtime And SPI Isolation

Core storage, carrier read/write operations, and EventBus propagation do not require the optional HTTP or Kafka clients. Forked-JVM tests run without those clients (or Redis, Elasticsearch, ServiceProxy, CircuitBreaker, Hazelcast, or JUnit), exercising every FlowId codec profile and event-loop/worker deployments with values, removals, and empty storage. Applications using a protocol adapter must provide that adapter's client dependency explicitly.

Additional forked applications exercise HTTP without Kafka and Kafka without WebClient in all three codec profiles. HTTP coverage uses loopback requests and responses; Kafka coverage uses the real Vert.x producer wrapper with `MockProducer` and controlled consumer records. These tests check runtime dependency isolation, not compatibility with a live Kafka broker.

Kafka-only forked tests use the same client-independent codec and configuration SPI fixtures. They verify asynchronous replacements/removals across two consumer scopes, private-storage isolation, and independently decoded objects in every FlowId profile. Both consumer scopes may change their local state without changing the original producer's values or removal markers; Kafka acknowledgments do not apply HTTP-style return propagation. These checks use `MockProducer` and controlled consumer records, not a live broker.

== Map Storage And Codec Coverage

Unit tests cover immutable input copies and collection views, exact generic declarations including empty maps, raw misuse, atomic batches and failures, explicit lifecycle rules, 256 concurrent entry additions, and event-loop/worker/virtual-thread deployment.

Forked core-only applications register real external codec and factory providers. They verify EventBus call/reply, values versus empty snapshots versus removals, explicit reintroduction, timer identity, cached factory discovery, and preservation of the separate FlowId in all three deployment modes and all FlowId writer profiles. Additional direct HTTP-carrier checks validate envelope export/import and send-time snapshots without requiring WebClient.

Separate loopback HTTP tests use real WebClient/server exchanges over HTTP/1.1, HTTP/2 upgrade/prior knowledge with both implementations, and trusted-TLS HTTP/3. They cover all three containers, coordinated in-flight caller edits, returned replacement/removal, absent metadata, private storage isolation, and timers, asserting actual wire versions. See link:reference.adoc#_collection_transport_coverage[collection transport coverage] for the matrix and limits.

Kafka-only tests use the native mock producer to verify send-time snapshots, map edits/removals forwarded across two scoped consumers, and preservation of the producer's newer map through acknowledgments. No live broker is required or tested.

A separate multi-JVM Hazelcast fixture verifies map values, typed empty maps, removals, and absence across the network. Returned map replacements/removals overwrite pending caller edits without changing its current FlowId; private storage remains local. Coordinated eight-request batches additionally verify map isolation while requests overlap across all caller threading models. Direct EventBus and generated ServiceProxy success paths run this matrix. Controlled ServiceProxy failures also return map replacements/removals; sixteen-call mixed success/failure batches verify isolation and unchanged native error semantics. Coordinated clustered timeout cases release remote replies only after expiration, verify actual late map headers, and check unchanged caller references and current map state on the next remote call. Three-JVM forwarding additionally covers middle-node replacement, removal, creation/reintroduction, and successful/failed returns.

Separate local generated-ServiceProxy tests cover native no-handler failures, timeouts, and deliberately late map replacements/removals. They verify actual late headers, unchanged caller references after expiration, and current map contents/removal/absence on a subsequent call across all three caller threading models. They do not add clustered timeout coverage.

Codec/carrier tests reject invalid map schemas, malformed envelopes, null/non-string values, and duplicate metadata headers without replacing prior storage. Healthy metadata still imports and the next valid map recovers, even when the error observer throws. Valid Unicode/empty/removal round trips cover both HTTP and Kafka carriers.

mvn -Dtest=ContextMapTest,ContextCollectionsIntegrationTest,ContextItemFactoriesTest test

== Set Storage And Codec Coverage

Tests cover defensive copies and iterator protection, equality-based uniqueness, atomic batch failures, empty/removal distinctions, raw misuse and type conflicts, factory matching, concurrent duplicate insertion with exactly one winner, and 256 additional concurrent unique insertions through public APIs on Vert.x-managed tasks.

The shared collection forked fixture discovers actual external codecs and factories without optional clients or JUnit on its runtime classpath. It checks EventBus request/reply, empty snapshots, whole-item removal, reintroduction, timer identity, caller FlowId preservation, and direct HTTP-carrier snapshots across all three deployment modes and FlowId writer profiles.

Separate loopback HTTP tests exercise real WebClient/server exchanges over HTTP/1.1, HTTP/2 upgrade/prior knowledge with both implementations, and trusted-TLS HTTP/3, asserting actual wire versions. They include membership changes while a request is pending and returned whole-set replacement/removal, distinguishing absence, empty sets, and removal markers without implicit factories. See link:reference.adoc#_collection_transport_coverage[collection transport coverage] for the matrix and limits.

Kafka-only tests use the native mock producer to verify send-time membership snapshots and edited sets/removals forwarded across two isolated consumer scopes. Consumer changes never return through producer acknowledgments; this is adapter coverage without a live broker.

A separate multi-JVM Hazelcast fixture validates set membership, typed emptiness, removal markers, and absence over the network, including returned whole-set replacements/removals after caller edits. Coordinated eight-request batches verify isolated membership/removal state during overlap across all caller threading models. Direct EventBus and generated ServiceProxy success paths reach the remote worker. Controlled ServiceProxy failures also return whole-set replacements/removals; sixteen-call mixed success/failure batches verify isolation without changing native error semantics. Coordinated clustered timeout cases inspect actual late set headers while preserving the expired caller's references and membership/removal/absence on the next remote call. Three-JVM forwarding includes middle-node replacement, removal, creation/reintroduction, and successful/failed returns.

Separate local generated-ServiceProxy tests cover native no-handler failures, timeouts, and deliberately late set replacements/removals. Actual late headers are inspected while caller membership/removal/absence remains unchanged and is verified on the next call across all three caller threading models. These are not clustered timeout tests.

Codec/carrier checks reject duplicate set elements, invalid/null element types, malformed envelopes, wrong shapes/versions, and duplicate metadata headers. Prior storage and healthy metadata survive rejection, the next valid set recovers, and observer failures cannot expose private payload text. Valid Unicode/empty/removal round trips use both HTTP and Kafka carriers.

== List Storage And Codec Coverage

Tests cover immutable input copies and list views, order and duplicate retention, bounds failures without partial mutation, raw element/declaration misuse, lifecycle rules, and factory matching. Concurrent public appends verify 264 retained positions, eight duplicate elements, distinct assigned indexes, and each writer's relative sequence, using Vert.x-managed tasks.

The shared map/set/list forked fixture discovers real external codecs and factories without optional clients or JUnit. It exercises EventBus request/reply, ordered duplicates, empty snapshots, whole-item removal/reintroduction, timer identity, caller FlowId preservation, and direct HTTP-carrier snapshots across all three deployment modes and FlowId writer profiles.

Separate loopback HTTP tests use real WebClient/server exchanges over HTTP/1.1, HTTP/2 upgrade/prior knowledge with both implementations, and trusted-TLS HTTP/3, asserting actual wire versions. They verify sequence/duplicate retention, in-flight caller edits, returned whole-list replacement/removal, absence, private storage isolation, and timer identity. See link:reference.adoc#_collection_transport_coverage[collection transport coverage] for the matrix and limits.

Kafka-only tests use the native mock producer to verify send-time list snapshots, positional edits and duplicates, and whole-list removals forwarded across two consumer scopes. Producer acknowledgments retain the producer's newer list rather than importing consumer changes. No live broker is exercised.

A separate multi-JVM Hazelcast fixture validates list order/duplicates, typed empty lists, removal markers, and absence over the network. Returned whole-list replacements/removals overwrite pending caller edits while older snapshots stay unchanged. Coordinated eight-request batches verify per-request sequence/duplicate retention and removal isolation across all caller threading models. Direct EventBus and generated ServiceProxy success paths run this matrix against a remote worker. Controlled ServiceProxy failures also return list replacements/removals; sixteen-call mixed success/failure batches verify per-request sequences and native error semantics. Coordinated clustered timeout cases inspect actual late list headers and preserve the expired caller's references and current sequence/removal/absence on the next remote call. Three-JVM forwarding also verifies middle-node replacement, removal, creation/reintroduction, and sequence retention through successful/failed returns.

Separate local generated-ServiceProxy tests cover native no-handler failures, timeouts, and deliberately late list replacements/removals. They inspect late wire headers, preserve the expired caller's snapshot references, and verify current order/duplicates or removal/absence on the next call across all three caller threading models. They do not add clustered timeout coverage.

Codec/carrier tests preserve list duplicates and reject malformed/versioned envelopes, wrong shapes, null/non-string elements, and duplicate metadata headers. Invalid input leaves prior storage intact, healthy metadata still imports, and a valid retry recovers even with a throwing error observer. Unicode/empty/removal round trips use both HTTP and Kafka carriers.

mvn -Dtest=ContextListTest,ContextCollectionsIntegrationTest,ContextItemFactoriesTest test
